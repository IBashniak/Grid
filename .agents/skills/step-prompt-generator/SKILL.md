## 2. Железные правила генерации ТЗ (`step<N>.md`)

1. **Изоляция и обратная совместимость:**
   - Новый этап создается в **отдельной папке** (`source/grid_<tech>/`, используя нижнее подчеркивание `snake_case` для валидного имени Python-пакета).
   - Файлы предыдущих этапов **никогда не изменяются и не удаляются**.
   - Тесты для нового этапа добавляются в `tests/` как новые отдельные файлы (`test_<tech>_*.py`), чтобы старые тесты продолжали проходить 100%.

2. **Ориентация на Junior-разработчика:**
   - Код должен быть простым и понятным, без избыточного оверинжиниринга, метаклассов и сложных абстракций.
   - Строгие Type Hints везде.
   - Подробные комментарии на русском языке к каждому логическому блоку.
   - Никаких однобуквенных переменных (кроме счетчика `i`).

3. **Обязательная связка из ДВУХ документов в `docs/`:**
   - `stage<N>_explanation.md`: инженерное руководство (архитектура, компоненты, жизненный цикл, пошаговая инструкция по запуску/развертыванию).
   - `stage<N>_complex_concepts.md`: подробный разбор 5 сложных тем простым языком по формуле:
     * *Житейская аналогия*
     * *Что происходит под капотом (ОС, ядро, сеть, память)*
     * *Сравнение кода (Антипаттерн vs Best Practice)*
     * *Как это решено в нашем проекте*
     * *Шпаргалка для защиты (Топ вопросов преподавателя)*

## 3. Обязательная структура генерируемого файла `step<N>.md`

Каждый генерируемый файл `step<N>.md` ДОЛЖЕН строго содержать 8 разделов:

### 1. Роль и цель
- Роль: Senior Engineer по соответствующему стеку (Distributed Systems, Cloud/DevOps, Chaos/FinOps) и ментор.
- Цель этапа: понятный, чистый и надежный код на Python/манифесты.
- Фокус: не на физике энергосетей, а на распределенных вычислениях, архитектуре, надежности и замерах производительности.

### 2. Структура создаваемых файлов
Дерево каталогов с указанием конкретных имен:
- `source/grid_<tech>/` (модули решения, точка входа CLI).
- `tests/` (минимум 2–3 новых файла тестов на pytest).
- `docs/` (`stage<N>_explanation.md` и `stage<N>_complex_concepts.md`).

### 3. Пошаговые требования к реализации кода (Шаги 1–5)
- **Шаг 1:** Интеграция с топологией IEEE-118 и подготовка данных (Object Store / Docker Volume / K8s ConfigMap).
- **Шаг 2:** Вычислительные воркеры и адаптация Монте-Карло под целевую среду (Ray tasks / Container workers / K8s Job Pods).
- **Шаг 3:** Диспетчеризация, координация и балансировка нагрузки (Scheduler / Queue / HPA / Tracing).
- **Шаг 4:** Бенчмаркинг, замер времени, Throughput, Speedup и экспорт метрик в JSON (`benchmark_results_<tech>.json`).
- **Шаг 5:** Интерфейс запуска и управления (CLI скрипт с подкомандами или единая точка входа).

### 4. Требования к коду (Junior-friendly)
- Правила именования, типизация, комментарии, отсутствие «магических чисел».

### 5. Выделение 5 сложных концепций `[DEEP DIVE / СЛОЖНАЯ КОНЦЕПЦИЯ]`
- Точный список 5 тем, специфичных для данного этапа (см. матрицу тем ниже).

### 6. Требования к автоматическим тестам (`pytest`)
- Минимум 3 сценария тестов (позитивные, негативные с валидацией ошибок, проверка корректности выходного JSON).
- Тесты должны выполняться быстро (< 10–15 сек) и автономно.

### 7. Требования к документации (`docs/`)
- Требования к `stage<N>_explanation.md`.
- Требования к `stage<N>_complex_concepts.md`.

### 8. Definition of Done (Критерии приемки)
- Чеклист для человека (ручная проверка ментором): запуск одной командой, код завершения 0, создание JSON-файла, наличие документации.
- Чеклист для pytest: 100% pass (0 failed, 0 errors).

## 4. Матрица тем `[DEEP DIVE]` для каждого этапа

### Этап 1 (MIMD на CPU):
1. **GIL (Global Interpreter Lock):** почему `multiprocessing`, а не `threading`.
2. **Сериализация (Pickle IPC):** передача через сокеты/пайпы, top-level воркеры, налог на сериализацию.
3. **Изоляция Seed в процессах:** почему нельзя общий `random.seed()`, клонирование памяти при `fork()`.
4. **Закон Амдала:** почему 8 ядер не дают 8.0x (последовательная фракция $s$).
5. **Санитарная обработка Z-score:** устранение артефактов `capacity <= 0` в датасетах.

### Этап 2 (Грид-кластер Ray Grid):
1. **Ray Object Store & Zero-Copy (`ray.put`):** Plasma shared memory, исключение дублирования в RAM.
2. **Ray Task vs Ray Actor:** stateless функции vs stateful микросервисы.
3. **Проблема Stragglers и динамическая диспетчеризация:** почему барьер `ray.get` разрушает кластер, решение через `ray.wait`.
4. **Закон Густафсона-Барсиса:** почему при масштабировании кластера растет объем вычислений ($N \to 10^7$).
5. **Отказоустойчивость задач (Fault Tolerance):** `max_retries`, Heartbeats, Lineage reconstruction при вылете ноды.

### Этап 3 (Docker & Microservices):
1. **cgroups и namespaces ядра Linux:** как Docker изолирует CPU/память без виртуализации "железа".
2. **Архитектура асинхронных очередей (Decoupled Architecture):** почему Web API никогда не считает Монте-Карло синхронно, паттерн Producer-Consumer (Redis/Celery/RQ).
3. **Docker Compose Networking & DNS:** как сервисы находят друг друга по именам контейнеров без жестких IP.
4. **Graceful Shutdown и сигналы Linux:** как воркер должен реагировать на `SIGTERM` (завершение текущего чанка) и `SIGKILL`.
5. **Оптимизация Docker Image (Multi-stage builds):** почему нельзя пихать компиляторы в продакшн-образ и как уменьшить размер с 2 ГБ до 150 МБ.

### Этап 4 (Kubernetes & Cloud Orchestration):
1. **Quality of Service (QoS) и OOM Killer:** разница между `requests` и `limits`, почему K8s убивает поды с Exit Code 137.
2. **K8s Job vs Deployment:** почему batch-вычисления Монте-Карло оформляются как `Job` / `CronJob`, а не `Deployment`.
3. **Горизонтальное автомасштабирование (HPA / KEDA):** масштабирование не по утилизации CPU (которая в Монте-Карло всегда 100%), а по глубине очереди задач.
4. **ConfigMaps и Secrets:** разделение неизменяемого контейнера и динамической конфигурации сети IEEE-118.
5. **Сетевые оверхеды K8s (Overlay CNI):** как инкапсуляция пакетов (VXLAN/Geneve) влияет на время передачи чанков.

### Этап 5 (Chaos Engineering & FinOps):
1. **Распределенное трассирование (OpenTelemetry / Jaeger):** как Trace ID и Span ID связывают цепочку вычислений через десятки серверов.
2. **Модель стоимости облака (FinOps TCO):** On-Demand vs Reserved vs Spot инстансы, анализ точки безубыточности.
3. **Формула Янга/Дейли (Optimal Checkpoint Interval):** $\tau \approx \sqrt{2 \cdot \delta \cdot M}$ — как математически рассчитать идеальную частоту сохранения состояния на Spot-нодах.
4. **Анализ перцентилей задержки (Tail Latency P90/P99):** почему среднее арифметическое (Mean) скрывает катастрофические проблемы кластера.
5. **Теория хаос-инженерии (Chaos Monkey / Fault Injection):** почему падение нод в проде должно тестироваться штатно, а не становиться ночной тревогой.

## 5. Алгоритм действий при получении запроса от пользователя

Когда пользователь просит создать промпт для Шага $N$:
1. Определи номер шага $N$.
2. Возьми соответствующую строку из матрицы этапов и карту `[DEEP DIVE]`.
3. Сгенерируй полноценный, детальный, законченный Markdown-файл `Igor-grid/step<N>.md` строго по 8 каноническим разделам.
4. Убедись, что все пути ведут в `source/grid_<tech>/`, тесты в `tests/test_<tech>_*.py`, а документация включает ОБА файла: `stage<N>_explanation.md` и `stage<N>_complex_concepts.md`.
5. Предоставь пользователю краткий дайджест с кликабельной ссылкой на созданный файл `step<N>.md`.
