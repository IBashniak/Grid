# Обучающее руководство: Этап 1 — Параллельные вычисления MIMD на CPU

Данный документ представляет собой подробное руководство по архитектуре, устройству кода и ключевым концепциям параллельных вычислений на примере симуляции надежности энергосистемы IEEE-118 методом Монте-Карло.

---

## 1. Архитектурный обзор и схема потока данных

Проект реализует вычислительную парадигму **MIMD (Multiple Instruction, Multiple Data)** согласно классификации Флинна. В отличие от SIMD (где все ядра синхронно выполняют одну инструкцию над вектором чисел), при MIMD каждое ядро процессора выполняет свой независимый поток команд над своим собственным набором данных.

Каждое испытание методом Монте-Карло моделирует независимый сценарий аварии (стохастический каскад), поэтому испытания не требуют синхронизации между собой (**Embarrassingly Parallel Workload**).

### Схема потока данных (Data Flow):

```text
[ Диск: Datasets/ (Blist, Ef, Bf) ]
               │
               ▼  (1. Чтение и санитарная обработка Z-score)
   ┌───────────────────────┐
   │ GridTopology (Память) │
   │ 118 узлов, 186 ветвей │
   └───────────────────────┘
               │
               ▼  (2. Чанкование: 10 000 испытаний / 4 воркера = 4 чанка по 2500)
   ┌─────────────────────────────────────────────────────────────┐
   │                 multiprocessing.Pool(4)                     │
   │                                                             │
   │  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌─────┐ │
   │  │ Воркер 0     │ │ Воркер 1     │ │ Воркер 2     │ │ ... │ │
   │  │ Chunk 0      │ │ Chunk 1      │ │ Chunk 2      │ │     │ │
   │  │ seed: 42..   │ │ seed: 2542.. │ │ seed: 5042.. │ │     │ │
   │  └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ └─┬───┘ │
   └─────────┼────────────────┼────────────────┼───────────┼─────┘
             │                │                │           │
             ▼                ▼                ▼           ▼
   (3. Локальная агрегация: blackouts, trips, dns_sum, branch_trips)
             │                │                │           │
             └────────────────┼────────────────┼───────────┘
                              ▼  (4. Сбор через IPC Pickle)
               ┌──────────────────────────────┐
               │  Координатор (Main Process)  │
               │   Расчет Speedup, Throughput │
               │   Топ-5 критических ветвей   │
               └──────────────┬───────────────┘
                              ▼  (5. Экспорт метрик)
              [ benchmark_results_mimd_grid.json ]
```

## 2. Разбор модулей и классов

### 2.1. `topology.py` (Модель данных и граф)
- **`Branch`**: Датакласс, описывающий отдельную линию электропередачи (ветвь). Хранит идентификатор, узлы начала и конца (`from_bus`, `to_bus`), начальный поток мощности (`flow`), предел пропускной способности (`capacity`) и статус (`active: True/False`).
- **`Bus`**: Датакласс узла (подстанции / шины). Хранит идентификатор и текущую нагрузку (`load`).
- **`GridTopology`**: Представление всей энергосети. Содержит списки узлов, ветвей и оптимизированный словарь смежности `adjacency: dict[int, list[int]]`, позволяющий мгновенно за $O(1)$ находить все линии, подключенные к заданной подстанции.
- **`sanitize_branch_capacity(...)`**: Защитная функция нормализации. Устраняет артефакты нормализации датасета, гарантируя физическую корректность (`capacity > 0`).
- **`build_topology_from_data(...)`**: Фабричный метод, загружающий реальные матрицы PowerGraph IEEE-118 или создающий детерминированный синтетический граф сети (118 узлов, 186 линий), если внешние файлы отсутствуют.

### 2.2. `engine.py` (Вычислительный движок Монте-Карло)
- **`run_single_trial(...)`**: Реализует одно изолированное стохастическое испытание:
  1. Создает локальный генератор случайных чисел `random.Random(seed)`.
  2. Моделирует первичный шок (N-k авария): отключает $k$ случайных линий.
  3. Запускает каскадный цикл: пытается перераспределить потерянную мощность отключенных линий на смежные активные линии пропорционально их свободному резерву `(capacity - flow)`.
  4. Проверяет перегрузки: линии с $|flow| > capacity$ отключаются защитными реле, вызывая следующую волну каскада.
  5. Возвращает метрики: флаг блэкаута (`blackout`), число каскадных отключений (`cascade_trips`), долю потерянной мощности (`dns_proxy`).
- **`simulate_trials_chunk(...)`**: Функция воркера верхнего уровня. Получает пакет задач (например, 2500 испытаний), последовательно выполняет их и возвращает компактную агрегированную статистику вместо миллионов отдельных объектов.

### 2.3. `benchmark.py` (Оркестратор параллелизма и метрики)
- **`partition_trials(...)`**: Разбивает общее число испытаний на пакеты без перекоса нагрузки.
- **`run_benchmark(...)`**: Управляет жизненным циклом бенчмарка:
  1. Замеряет базовое время выполнения на одном ядре ($T_1$).
  2. Запускает пул процессов через `multiprocessing.Pool(num_workers).map(...)`.
  3. Вычисляет ускорение ($Speedup = T_1 / T_n$) и пропускную способность (траекторий/сек).
  4. Формирует Топ-5 наиболее уязвимых линий электропередачи.
  5. Сохраняет итоговый отчет в формате JSON.

### 2.4. `main.py` (CLI интерфейс)
- Точка входа в программу.
- Реализует удобный парсинг аргументов с валидацией (`--trials`, `--workers`, `--k`, `--data`, `--out`).
- Защищена блоком `if __name__ == '__main__':`.

## 3. Пошаговый жизненный цикл одного запуска

Рассмотрим, что происходит в операционной системе, когда пользователь выполняет команду:
```bash
python source/grid-mimd/main.py --trials 10000 --workers 4 --k 2
```

1. **Парсинг аргументов (CLI Phase):**
   `argparse` проверяет переданные параметры. Если $k \notin [1, 5]$, программа аварийно завершается с информативным сообщением. При корректных параметрах управление передается в `run_benchmark(...)`.
2. **Инициализация топологии:**
   С диска считываются матрицы сети IEEE-118. Проверяются емкости линий, создаются 118 объектов `Bus` и 186 объектов `Branch`. Строится словарь смежности.
3. **Чанкование (Chunking):**
   10 000 испытаний делятся на 4 равных пакета по 2500 задач:
   - Chunk 0: 2500 задач, базовый seed = 42
   - Chunk 1: 2500 задач, базовый seed = 2542
   - Chunk 2: 2500 задач, базовый seed = 5042
   - Chunk 3: 2500 задач, базовый seed = 7542
4. **Калибровка базовой производительности ($T_1$):**
   На одном ядре выполняется тестовая выборка (например, 1000 испытаний), чтобы зафиксировать эталонную скорость одного ядра для честного расчета ускорения.
5. **Создание пула процессов (Fork / Spawn):**
   Главный процесс создает 4 независимых дочерних процесса операционной системы через `multiprocessing.Pool(4)`. Входные аргументы упаковываются через `pickle` и передаются через системные каналы (IPC Pipes).
6. **Параллельные вычисления (MIMD Execution):**
   Все 4 ядра работают на 100% мощности параллельно. Каждое ядро генерирует уникальные аварии и независимо рассчитывает физику каскадов.
7. **Сбор результатов и агрегация (Reduce Phase):**
   Воркеры сериализуют словари с суммами и возвращают их в главный процесс. Главный процесс суммирует счетчики отключений каждой линии и вычисляет итоговую вероятность блэкаута.
8. **Формирование отчета:**
   Рассчитывается $Speedup = T_1 / T_4$, выявляются 5 линий с наибольшим числом отказов, и данные сохраняются в `benchmark_results_mimd_grid.json`.

## 4. Разбор сложных концепций [DEEP DIVE]

### 4.1. GIL (Global Interpreter Lock)
> **Вопрос:** Почему в Python для CPU-bound вычислений мы берем `multiprocessing`, а не `threading`?

- **Суть проблемы:** В стандартном интерпретаторе CPython управление памятью не является потокобезопасным. Чтобы избежать повреждения внутренних структур интерпретатора, введен механизм GIL (Global Interpreter Lock) — глобальная блокировка, которая разрешает выполнение инструкций Python в каждый момент времени только одному системному потоку.
- **Аналогия:** Представьте кухню ресторана, где есть 4 повара, но всего **одна поваренная книга** (интерпретатор), и читать рецепт может только один повар одновременно. Пока один повар режет салат, остальные трое стоят и ждут своей очереди к книге.
- **Решение:** Модуль `multiprocessing` открывает 4 **отдельные кухни**, у каждого повара свой стол, своя поваренная книга и свои продукты. Они работают одновременно, не мешая друг другу.

### 4.2. Сериализация (Pickle IPC)
> **Вопрос:** Почему функции для `Pool.map` должны быть функциями верхнего уровня модуля, и почему нельзя передавать гигантские несериализуемые объекты?

- **Суть проблемы:** Дочерние процессы ОС находятся в изолированных адресных пространствах оперативной памяти. Они не могут напрямую читать переменные родительского процесса. Передача данных между процессами осуществляется через каналы межпроцессного взаимодействия (IPC Pipes) с помощью сериализации (модуль `pickle`).
- **Ограничения:**
  1. `pickle` не умеет передавать замыкания (вложенные функции) и лямбды, так как дочерний процесс восстанавливает функцию по ее пути импорта (`module.function_name`). Функция должна быть объявлена на верхнем уровне модуля.
  2. Сериализация и десериализация тяжелых объектов требует значительного времени CPU и памяти.
- **Аналогия:** Если вам нужно отправить другу в другой город инструкцию по сборке шкафа, вы отправляете компактное текстовое письмо (легкий кортеж аргументов), а не пытаетесь отправить по почте собранный дубовый шкаф целиком на каждое действие.

---

### 4.3. Изоляция Seed в процессах
> **Вопрос:** Почему нельзя использовать глобальный `random.seed()` в параллельных процессах?

- **Суть проблемы:** При создании процессов через системный вызов `fork()` дочерний процесс получает точный снимок памяти родителя, включая внутреннее состояние генератора псевдослучайных чисел `random`. Если вызвать `random.seed(42)` до создания пула, все 4 воркера начнут генерировать абсолютно одинаковую последовательность псевдослучайных чисел. В результате вместо 10 000 уникальных сценариев вы получите 2 500 одинаковых сценариев, повторенных 4 раза!
- **Аналогия:** Крупье в казино перед игрой ксерокопирует уже разложенную колоду карт и раздает одинаковые копии четырем столам. На всех четырех столах игроки получат одинаковые карты.
- **Решение:** Мы создаем индивидуальный изолированный объект `random.Random(seed)` внутри каждого испытания, где `seed = base_seed + trial_index`. Каждый сценарий гарантированно уникален и детерминирован.

---

### 4.4. Закон Амдала (Amdahl's Law)
> **Вопрос:** Почему ускорение при 8 воркерах никогда не составит ровно 8.0x?

- **Суть проблемы:** Закон Амдала утверждает, что максимальное ускорение программы ограничено долей работы, которая выполняется последовательно ($s = 1 - p$):
  $$Speedup \le \frac{1}{s + \frac{1 - s}{N}}$$
  В нашей программе последовательными являются:
  - чтение топологии с диска;
  - создание дочерних процессов операционной системой;
  - упаковка и распаковка данных в IPC (Pickle);
  - финальная агрегация и сохранение JSON.
- **Аналогия:** Вы заказали пиццу. Пиццерия наняла 10 поваров, и пиццу теперь выпекают всего за 1 минуту вместо 10 минут. Но курьеру на мопеде по пробкам всё равно нужно ехать до вашего дома 20 минут. Общее время ожидания сократилось с 30 минут до 21 минуты (ускорение всего 1.4x, а не 10x).

### 4.5. Обработка Z-score артефактов
> **Вопрос:** Почему численные данные из MATLAB/ML-датасетов требуют санитарной обработки физических ограничений (`capacity <= 0`)?

- **Суть проблемы:** В научных датасетах (включая PowerGraph) исходные данные часто проходят математическую стандартизацию:
  $$z = \frac{x - \mu}{\sigma}$$
  В результате признак пропускной способности (номинальной емкости линии) может принять отрицательное значение (например, $-0.18$). Кроме того, в исходных таблицах энергосетей трансформаторы связи часто имеют тепловой предел $lr = 0$, так как их перегрузка лимитируется внешними реле. В алгоритме каскада при условии $|flow| > capacity$ линия с $capacity \le 0$ отключится мгновенно при любом ненулевом потоке.
- **Аналогия:** В карточке автомобиля в графе «максимальная скорость» стоит $-10$ км/ч или $0$ км/ч. Если система автопилота увидит это ограничение, она заблокирует машину сразу при включении зажигания.
- **Решение:** В функции `sanitize_branch_capacity` мы принудительно задаем безопасный технологический резерв: `capacity = max(1.0, 2.0 * abs(flow))`.

## 5. Инструкция по запуску и проверке

### 5.1. Установка окружения (Conda / venv)
Убедитесь, что активировано ваше окружение:
```bash
conda activate grid
```

### 5.2. Запуск основного бенчмарка
Запуск симуляции 10 000 испытаний на 4 ядрах процессора с первичной аварией степени $k=2$:
```bash
python source/grid-mimd/main.py --trials 10000 --workers 4 --k 2
```

Для быстрого теста на 1 000 испытаний:
```bash
python source/grid-mimd/main.py --trials 1000 --workers 2
```

### 5.3. Запуск автоматических тестов (pytest)
Для запуска полного набора тестов:
```bash
pytest tests/ -v
```

Все тесты выполняются со 100% успехом за 1–3 секунды.
