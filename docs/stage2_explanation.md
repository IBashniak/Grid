# Обучающее руководство: Этап 2 — Распределенный грид-кластер на базе Ray

Данный документ представляет собой инженерно-архитектурное руководство по **Этапу 2** сквозного проекта: переходу от локального многопроцессорного пула на одной машине (MIMD на CPU) к **гетерогенному распределенному грид-кластеру на базе фреймворка Ray** для моделирования каскадных аварий в энергосистеме IEEE-118 методом Монте-Карло.

---

## 1. Архитектурный обзор гетерогенного грид-кластера

На Этапе 1 мы были ограничены физическими ядрами одного компьютера (`multiprocessing.Pool`). Чтобы увеличить скорость симуляции в десятки раз и просчитать $10^6 \dots 10^7$ сценариев аварий, мы объединяем несколько разнородных компьютеров (ноутбуки, рабочие станции, серверы) по локальной сети в единый вычислительный **Грид-кластер (Compute Grid)** под управлением **Ray**.

### Схема архитектуры кластера Ray и потока данных:

```text
================================================================================
                ГЕТЕРОГЕННЫЙ ГРИД-КЛАСТЕР RAY (Локальная сеть LAN)
================================================================================

  ┌──────────────────────────────────────────────────────────────────────────┐
  │ УПРАВЛЯЮЩИЙ УЗЕЛ (Head Node: 192.168.1.10)                               │
  │                                                                          │
  │  ┌──────────────────────┐    ray.put(topo)    ┌───────────────────────┐  │
  │  │ Драйвер (run.py)     │ ──────────────────► │ Local Object Store    │  │
  │  │ DynamicRayScheduler  │                     │ (Plasma Shared Mem)   │  │
  │  │ Цикл ray.wait(...)   │                     │ [GridTopology: 1x]    │  │
  │  └──────────┬───────────┘                     └───────────┬───────────┘  │
  │             │                                             │              │
  │  ┌──────────▼───────────┐                     ┌───────────▼───────────┐  │
  │  │ GCS Server (:6379)   │                     │ Локальные воркеры     │  │
  │  │ Реестр узлов и задач │                     │ Zero-Copy чтение      │  │
  │  └──────────┬───────────┘                     └───────────────────────┘  │
  └─────────────┼─────────────────────────────────────────────┬──────────────┘
                │ Диспетчеризация чанков                      │ Репликация
                │ (легковесные ObjectRef)                     │ графа (1 раз на узел)
        ┌───────┴───────────────────────────────┐             │
        ▼                                       ▼             ▼
  ┌───────────────────────────────────┐   ┌───────────────────────────────────┐
  │ РАБОЧИЙ УЗЕЛ 1 (192.168.1.15)     │   │ РАБОЧИЙ УЗЕЛ 2 (192.168.1.22)     │
  │ Мощный ПК (8 ядер, быстрый)       │   │ Слабый ноутбук (2 ядра, Straggler)│
  │                                   │   │                                   │
  │ ┌───────────────────────────────┐ │   │ ┌───────────────────────────────┐ │
  │ │ Object Store (Plasma /dev/shm)│ │   │ │ Object Store (Plasma /dev/shm)│ │
  │ │ [Копия GridTopology: 1 шт.]   │ │   │ │ [Копия GridTopology: 1 шт.]   │ │
  │ └───────────────┬───────────────┘ │   │ └───────────────┬───────────────┘ │
  │                 │ Zero-Copy       │   │                 │ Zero-Copy       │
  │   ┌─────────┬───┴─────┬─────────┐ │   │       ┌─────────┴─────────┐       │
  │   ▼         ▼         ▼         ▼ │   │       ▼                   ▼       │
  │ [W1]      [W2]      [W3] ...  [W8]│   │     [W1]                [W2]      │
  │ Выполнил ~80% всех чанков!        │   │ Выполнил ~20% чанков без задержки │
  └───────────────────────────────────┘   └───────────────────────────────────┘
```

### Ключевые архитектурные компоненты Ray:
1. **Head Node (Управляющий узел):** Компьютер, на котором запущен координатор кластера — **GCS (Global Control Store)** на порту `6379` и веб-панель мониторинга Ray Dashboard (`8265`). Здесь же обычно запускается скрипт-драйвер (`run.py`).
2. **Worker Nodes (Рабочие узлы):** Дополнительные компьютеры в сети, подключенные к Head-узлу. Они предоставляют свои ядра CPU для выполнения задач.
3. **Raylet:** Системный демон на каждом узле, состоящий из двух частей: локального планировщика задач (Task Scheduler) и демона разделяемой памяти **Object Store (Plasma)**.
4. **Driver (Драйвер):** Процесс Python, выполняющий функцию `run_ray_benchmark()`, который раздает задачи (`@ray.remote`) и собирает агрегированные метрики через `ray.wait()`.

## 3. Выделение сложных концепций `[DEEP DIVE / СЛОЖНАЯ КОНЦЕПЦИЯ]`

В коде проекта реализованы и прокомментированы 5 фундаментальных концепций распределенных систем:

1. **`[DEEP DIVE]` Ray Object Store и Zero-Copy (`ray.put`)** — в `source/grid_ray/topology.py`:
   Топология сети помещается в разделяемую память Plasma ровно один раз через `topology_ref = ray.put(topo_data)`. Воркеры получают 28-байтную ссылку `ray.ObjectRef` вместо пересылки мегабайтных копий графа при каждом вызове задачи.
2. **`[DEEP DIVE]` Ray Task vs Ray Actor** — в `source/grid_ray/ray_engine.py`:
   Симуляция Монте-Карло использует несохраняющие состояние задачи (`@ray.remote def`), что позволяет планировщику свободно распределять чанки по любым узлам без привязки к конкретному процессу.
3. **`[DEEP DIVE]` Проблема Stragglers и динамическая диспетчеризация (`ray.wait`)** — в `source/grid_ray/scheduler.py`:
   Вместо жесткого барьера `ray.get(all_futures)` используется цикл `ray.wait(active_futures, num_returns=1, timeout=0.1)` с мелким дроблением задач (в 2–4 раза больше числа ядер кластера). Быстрые узлы автоматически забирают больше работы.
4. **`[DEEP DIVE]` Закон Густафсона-Барсиса (Gustafson-Barsis's Law)** — в `source/grid_ray/benchmark.py`:
   Объясняет, почему при масштабировании размера задачи ($N \to 10^5 \dots 10^7$ испытаний) доля последовательных накладных расходов стремится к нулю, а эффективность кластера остается высокой.
5. **`[DEEP DIVE]` Отказоустойчивость задач (Fault Tolerance & Retries)** — в `source/grid_ray/ray_engine.py`:
   Декоратор `@ray.remote(max_retries=3, retry_exceptions=True)` в сочетании с детерминированным расчетом `seed = base_seed + i` гарантирует, что при обрыве связи с воркером задача будет безопасно пересчитана на другом узле с идентичным результатом.

> Подробный разбор всех 5 концепций с житейскими аналогиями, примерами антипаттернов и шпаргалкой для защиты находится в соседнем документе: `docs/stage2_complex_concepts.md`.

## 4. Пошаговый жизненный цикл распределенного запуска

Что происходит внутри кластера, когда вы вводите команду:
```bash
python source/grid_ray/run.py load --trials 100000 --head 192.168.1.10:6379 --k 2
```

1. **Подключение к GCS (`ray.init`):**
   Скрипт-драйвер соединяется с управляющим узлом `192.168.1.10:6379`. Через `ray.nodes()` и `ray.cluster_resources()` он опрашивает реестр живых машин (например: 3 узла, суммарно 12 ядер CPU).
2. **Публикация топологии в Object Store (`prepare_cluster_topology`):**
   Драйвер собирает граф `GridTopology` (118 узлов, 186 линий электропередачи) и вызывает `topo_ref = ray.put(topology)`. Граф сохраняется в локальной памяти Plasma, а переменная `topo_ref` получает компактный идентификатор `ObjectRef(...)`.
3. **Калибровка одного ядра:**
   Для честного расчета метрики ускорения (`speedup_vs_single_cpu`) драйвер прогоняет мини-пакет (до 500 испытаний) на одном локальном ядре и экстраполирует базовое время $T_1$.
4. **Планирование чанков (`DynamicRayScheduler`):**
   Для 12 ядер кластера и коэффициента дробления 3 планировщик разбивает 100 000 испытаний на $12 \times 3 = 36$ небольших чанков (по ~2778 испытаний). Для каждого чанка вычисляется уникальный непересекающийся `base_seed`.
5. **Скользящее окно и `ray.wait`:**
   - Планировщик отправляет стартовое окно задач в кластер через `simulate_trials_chunk_remote.remote(...)`, передавая легковесный `topo_ref`.
   - Когда первый чанк попадает на удаленный ноутбук `192.168.1.15`, его демон Raylet **один раз** скачивает `GridTopology` по сети в свой локальный `/dev/shm`. Все последующие чанки на этом ноутбуке берут граф мгновенно из общей оперативной памяти (Zero-Copy).
   - Драйвер крутится в неблокирующем цикле `ray.wait(active_futures, num_returns=1, timeout=0.1)`. Как только любой воркер завершает чанк, драйвер забирает компактный словарь статистики и тут же отправляет освободившемуся воркеру следующий чанк из очереди.
6. **Агрегация и сохранение отчета:**
   Когда все 36 чанков собраны, драйвер суммирует счетчики блэкаутов и отключений каждой из 186 линий, определяет Топ-5 самых уязвимых ветвей сети, рассчитывает `throughput_trials_per_sec`, `speedup_vs_single_cpu`, `cluster_efficiency_percent` и сохраняет файл `benchmark_results_ray_grid.json`.

## 5. Практическое руководство: Как объединить 2–3 ноутбука в единый грид-кластер по Wi-Fi / LAN

Вы можете развернуть настоящий распределенный грид-кластер прямо в учебной аудитории или дома из 2–3 ноутбуков (Linux, macOS, Windows).

### Шаг 0. Золотые правила совместимости окружения
Перед объединением машин убедитесь, что на **всех** компьютерах:
1. Все ноутбуки подключены к **одной и той же локальной сети** (один Wi-Fi роутер или коммутатор Ethernet).
2. Совпадают минорные версии **Python** (например, на всех машинах `Python 3.11.x` или `Python 3.12.x`). *Если на Head-узле Python 3.12, а на воркере Python 3.10 — сериализация байткода и `pickle` протоколов завершится ошибкой!*
3. Совпадает версия библиотеки **Ray** (`pip install "ray[default]==2.9.3"` или актуальная единая версия).
4. Склонирован одинаковый код проекта `Igor-grid`.

---

### Шаг 1. Узнаем локальный IP-адрес главного ноутбука (Head Node)
В локальной сети адрес всегда начинается на `192.168.x.x`, `10.x.x.x` или `172.16-31.x.x` (не путайте с петлевым адресом `127.0.0.1`!).

- **Linux:**
  ```bash
  hostname -I | awk '{print $1}'
  # или: ip -4 addr show
  ```
- **macOS:**
  ```bash
  ipconfig getifaddr en0
  ```
- **Windows (PowerShell / CMD):**
  ```powershell
  ipconfig
  # Ищите строку "IPv4-адрес" у адаптера Беспроводной сети (Wi-Fi)
  ```
Допустим, IP вашего главного ноутбука: **`192.168.1.10`**.

---

### Шаг 2. Запускаем управляющий узел (Head Node) на ПК №1
На главном компьютере (`192.168.1.10`) выполните:
```bash
python source/grid_ray/run.py head --port 6379
```
Скрипт запустит координатор кластера и выведет готовую команду для подключения остальных машин.

---

### Шаг 3. Подключаем рабочие ноутбуки (Worker Nodes) на ПК №2 и ПК №3
На втором и третьем ноутбуках выполните команду, указанную на предыдущем шаге:
```bash
python source/grid_ray/run.py worker --head 192.168.1.10:6379
```
Проверить, что все узлы успешно вошли в кластер, можно с любого компьютера:
```bash
python source/grid_ray/run.py status --head 192.168.1.10:6379
```
Вы увидите суммарное число узлов (например, `Активных узлов: 3`), общее число ядер CPU и список IP-адресов всех участников.

---

### Шаг 4. Запускаем распределенный расчет Монте-Карло
Теперь на главном ноутбуке запустите распределенную симуляцию:
```bash
python source/grid_ray/run.py load --trials 100000 --head 192.168.1.10:6379 --k 2
```
В консоли отобразится распределение чанков по IP-адресам каждого ноутбука, общее время, ускорение и сгенерируется итоговый отчет `benchmark_results_ray_grid.json`.

После завершения экспериментов остановите фоновые демоны Ray на всех машинах:
```bash
python source/grid_ray/run.py stop
```

### Шаг 5. Решение типичных сетевых проблем (Troubleshooting)

1. **Воркер зависает при подключении к `192.168.1.10:6379` (`Unable to connect to GCS`):**
   - **Причина 1: Межсетевой экран (Firewall) блокирует входящие соединения.**
     - На **Ubuntu / Linux**: разрешите трафик внутри локальной подсети:
       ```bash
       sudo ufw allow from 192.168.1.0/24
       # или откройте порты Ray: sudo ufw allow 6379:6385/tcp && sudo ufw allow 8265/tcp && sudo ufw allow 10002:19999/tcp
       ```
     - На **Windows**: убедитесь, что профиль сети Wi-Fi установлен как **«Частная сеть» (Private Network)**, либо временно разрешите `python.exe` / `ray.exe` в Брандмауэре Защитника Windows.
   - **Причина 2: Изоляция клиентов на роутере (AP Client Isolation).**
     Публичные Wi-Fi сети (в университете или кафе) часто запрещают прямое общение ноутбуков друг с другом.
     - **Решение:** Включите точку доступа (Hotspot) на смартфоне или одном из ноутбуков и подключите все 2–3 машины к ней.
   - **Проверка доступности порта:** С ноутбука-воркера проверьте связь с Head-узлом:
     ```bash
     nc -zv 192.168.1.10 6379
     # или в Python: python -c "import socket; s=socket.create_connection(('192.168.1.10', 6379), 3); print('OK!')"
     ```

2. **Воркер подключился, но задачи падают с `ModuleNotFoundError: No module named 'ray_engine'`:**
   - **Причина:** Скрипт запускается из разных рабочих директорий, и на удаленном воркере Python не находит файлы `source/grid_ray/`.
   - **Решение:** Запускайте `run.py` из корневого каталога проекта `Igor-grid` на всех машинах, либо задайте переменную окружения:
     ```bash
     export PYTHONPATH="$PWD/source/grid_ray:$PYTHONPATH"
     ```
