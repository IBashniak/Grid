## 3. Пошаговые требования к реализации кода

### Шаг 1. Модель данных и топология (`topology.py`)
- Создай датаклассы:
  - `Branch`: поля `id: int`, `from_bus: int`, `to_bus: int`, `flow: float`, `capacity: float`, `active: bool`.
  - `Bus`: поля `id: int`, `load: float`.
  - `GridTopology`: списки `buses`, `branches`, и словарь смежности `adjacency: dict[int, list[int]]` для быстрого поиска соседних линий.
- Реализуй функцию `build_topology_from_data(...)` (или функцию-адаптер для вызова существующего `source/dataset_scripts/load_powergraph_cascades.py`):
  - Граф содержит ровно 118 узлов и 186 ветвей.
  - **Краевой случай нормализации (Z-score):** если в исходных данных `capacity <= 0` (трансформаторы с исходным $lr=0$), принудительно задай безопасный резерв: `capacity = max(1.0, 2.0 * abs(flow))`.

### Шаг 2. Логика одного испытания (`engine.py: run_single_trial`)
Реализуй изолированную функцию `run_single_trial(topo_data, k_fault, seed, max_steps=20)`:
1. Инициализируй локальный генератор `random.Random(seed)` (для изоляции случайных чисел между потоками).
2. Сделай легковесную локальную копию состояния линий (`active`, `flow`).
3. **Первичный шок (N-k):** отключи ровно `k_fault` случайных активных линий (`active = False`).
4. **Каскадный цикл (до `max_steps` или пока есть перегрузки):**
   - Для каждой отключившейся линии найди смежные активные линии через общие узлы.
   - Перераспредели потерянный поток отключенной линии между соседями пропорционально их свободному резерву `(capacity - flow)`.
   - Если свободных соседей нет, поток считается потерянным.
   - Проверь перегрузки: если `abs(flow) > capacity`, пометь линию как отключенную (`active = False`).
5. **Метрики завершения:**
   - `cascade_trips`: количество линий, отключенных защитой *после* первичного удара.
   - `dns_proxy`: доля потерянного навантажения (0.0…0.2).
   - `blackout`: `True`, если `dns_proxy > 0.05` (потеряно более 5% мощности).
   - Возвращай словарь с результатами испытания.

### Шаг 3. Воркер для пула процессов (`engine.py: simulate_trials_chunk`)
- Реализуй функцию верхнего уровня `simulate_trials_chunk(args_tuple)`:
  - Принимает кортеж аргументов: `(chunk_id, num_trials, base_seed, k_fault, topo_data)`.
  - В цикле выполняет `num_trials`, генерируя детерминированный `seed = base_seed + i`.
  - Агрегирует локальные результаты (число блэкаутов, частоту отключений каждой линии).
  - Возвращает агрегированный словарь чанка.

### Шаг 4. Бенчмаркинг и параллельный запуск (`benchmark.py`)
- Функция `run_benchmark(num_trials, num_workers, k_fault, data_dir, output_file)`:
  - Разделяет `num_trials` на равные пакеты (chunks) по числу воркеров.
  - Если `num_workers == 1`: запуск в основном процессе или через `Pool(1)` для получения базового времени $T_1$.
  - Если `num_workers > 1`: запускает `multiprocessing.Pool(num_workers).map(simulate_trials_chunk, tasks)`.
  - Замеряет точное время выполнения через `time.perf_counter()`.
  - Вычисляет:
    - Общее время ($T_{workers}$), Throughput (траекторий/сек);
    - Ускорение $Speedup = T_1 / T_n$;
    - Итоговую вероятность блэкаута $P(\text{blackout})$;
    - Топ-5 наиболее уязвимых линий (линии с максимальным числом отключений).
  - Сохраняет результаты в JSON по структуре:
    ```json
    {
      "benchmark_type": "MIMD_CPU_Grid",
      "timestamp": "ISO-8601",
      "config": { "trials": 10000, "workers": 4, "k_fault": 1 },
      "performance": { "execution_time_sec": 1.25, "throughput_trials_per_sec": 8000.0, "speedup": 3.4 },
      "metrics": { "blackout_probability": 0.012, "top_critical_branches": [12, 45, 87, 101, 14] }
    }
    ```

### Шаг 5. Консольный интерфейс (`main.py`)
- Аргументы командной строки через `argparse`:
  - `--trials` (default: 10000);
  - `--workers` (default: `os.cpu_count()`);
  - `--k` (валидация: целое число от 1 до 5, default: 1);
  - `--data` (путь к датасету, default: `Datasets`);
  - `--out` (путь к результирующему JSON, default: `benchmark_results_mimd_grid.json`).
- Блок `if __name__ == '__main__':` обязателен (для корректной работы `multiprocessing` на Windows/macOS/Linux).

## 5. Выделение сложных концепций (для будущего разбора)
В коде и в документе `stage1_explanation.md` явно пометь специальными блоками `[DEEP DIVE / СЛОЖНАЯ КОНЦЕПЦИЯ]` следующие темы:
1. **GIL (Global Interpreter Lock):** почему в Python для CPU-bound задач мы берем `multiprocessing`, а не `threading`.
2. **Сериализация (Pickle IPC):** почему функции для `Pool.map` должны быть функциями верхнего уровня модуля, и почему нельзя передавать гигантские несериализуемые объекты.
3. **Изоляция Seed в процессах:** почему нельзя использовать глобальный `random.seed()` в параллельных процессах (проблема генерации одинаковых аварий во всех воркерах).
4. **Закон Амдала:** почему ускорение при 8 воркерах никогда не составит 8.0x (накладные расходы на fork/spawn и сериализацию).
5. **Обработка Z-score артефактов:** почему численные данные из MATLAB/ML-датасетов требуют санитарной обработки физических ограничений (`capacity <= 0`).
