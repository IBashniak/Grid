# ТЕХНИЧЕСКОЕ ЗАДАНИЕ ДЛЯ ИИ-РАЗРАБОТЧИКА: Реализация Этапа 2 (Грид-кластер на базе Ray)

## 1. Роль и цель
Ты выступаешь в роли Senior Distributed Systems / Python Engineer и ментора. Твоя задача — составить понятный, надежный и архитектурно чистый код на Python для **Этапа 2** сквозного проекта (распределенная симуляция устойчивости энергосистемы IEEE-118 методом Монте-Карло на базе фреймворка **Ray**).

Целевая аудитория кода: **Junior-разработчик**, изучающий распределенные и грид-системы. Код должен быть прозрачным, следовать PEP 8, содержать строгие Type Hints, подробные комментарии на русском языке и объяснять физику межмашинного распределения задач без избыточного оверинжиниринга.

Акцент делается на **переходе от локального многопроцессорного пула (MIMD на одной машине) к гетерогенному грид-кластеру**:
- Использование распределенного хранилища объектов Ray (Object Store, Plasma, Zero-copy shared memory);
- Диспетчеризация stateless задач через `@ray.remote`;
- Борьба с проблемой отстающих узлов (Stragglers) через динамическую сборку результатов (`ray.wait`);
- Замер эффективности распределения и оценка закона Густафсона-Барсиса.

## 3. Пошаговые требования к реализации кода

### Шаг 1. Топология и распределенное хранилище объектов (`topology.py`)
- Переиспользуй и адаптируй датаклассы `Branch`, `Bus`, `GridTopology` и защитную функцию `sanitize_branch_capacity` из Этапа 1.
- Реализуй функцию подготовки топологии для кластера `prepare_cluster_topology(topo_data) -> ray.ObjectRef`:
  - Помещает объект `GridTopology` в локальный / распределенный **Ray Object Store** ровно **один раз** через `ray.put(topo_data)`.
  - Возвращает ссылку на объект (`ray.ObjectRef`).
  - **Запрещено** передавать тяжелый объект `GridTopology` по значению в каждый вызов `@ray.remote` воркера, чтобы исключить дублирование данных в памяти и сетевой оверхед.

### Шаг 2. Распределенный воркер симуляции (`ray_engine.py`)
- Реализуй удаленную задачу Ray (Ray Task) с декоратором `@ray.remote`:
  ```python
  @ray.remote(max_retries=3, retry_exceptions=True)
  def simulate_trials_chunk_remote(
      chunk_id: int,
      num_trials: int,
      base_seed: int,
      k_fault: int,
      topology_ref: ray.ObjectRef,
  ) -> dict[str, Any]:
  ```
- Особенности реализации:
  - Функция автоматически разрешает `topology_ref` через zero-copy shared memory на узле-исполнителе.
  - Логика одного испытания идентична каскадной модели Этапа 1 (изолированный `random.Random(seed)`, N-k отключение, пропорциональное перераспределение резервов, отключение перегруженных линий, расчет `cascade_trips`, `dns_proxy`, `blackout`).
  - Воркер возвращает компактный агрегированный словарь чанка (`chunk_id`, `num_trials`, `blackouts_count`, `cascade_trips_sum`, `dns_sum`, `branch_trips`).
  - Параметр `max_retries=3` обеспечивает автоматический повтор задачи при кратковременном сбое сетевого воркера.

### Шаг 3. Диспетчер задач и преодоление отстающих узлов (`scheduler.py`)
- В гетерогенном грид-кластере узлы имеют разную производительность (CPU, тактовая частота, нагрузка ОС). Жесткий `ray.get(futures)` приводит к простою быстрых узлов в ожидании самого медленного воркера (**проблема Stragglers**).
- Реализуй диспетчер `DynamicRayScheduler`:
  - Разбивает общий объем испытаний на небольшие чанки (размер чанка подбирается так, чтобы общее число задач превышало количество ядер в кластере в 2–4 раза, обеспечивая непрерывную загрузку).
  - Отправляет начальный пул задач воркерам через `simulate_trials_chunk_remote.remote(...)`.
  - Использует неблокирующий опрос готовых задач:
    ```python
    ready_refs, remaining_refs = ray.wait(active_futures, num_returns=1, timeout=0.1)
    ```
  - По мере завершения задач немедленно собирает их результаты и (при наличии нераспределенных испытаний) подбрасывает освободившемуся воркеру новую задачу.
  - Собирает метаданные: время выполнения каждого чанка и распределение по узлам (IP воркера).

### Шаг 4. Бенчмаркинг и распределенные метрики (`benchmark.py`)
- Функция `run_ray_benchmark(trials, k_fault, address=None, num_cpus=None, output_file=...)`:
  - Инициализирует Ray через `ray.init(address=address, num_cpus=num_cpus, ignore_reinit_error=True)`.
  - Собирает информацию о кластере: общее число активных узлов (`ray.nodes()`), суммарное число доступных CPU-ядер, список IP-адресов.
  - Помещает топологию сети в Object Store: `topo_ref = ray.put(topology)`.
  - Запускает симуляцию через `DynamicRayScheduler`.
  - Замеряет время выполнения через `time.perf_counter()`.
  - Рассчитывает:
    - Общее время ($T_{cluster}$), Throughput (траекторий/сек);
    - Ускорение относительно локального однопоточного базового времени ($Speedup$);
    - Коэффициент эффективности кластера ($Efficiency = \frac{Speedup}{N_{total\_cpus}} \times 100\%$);
    - Итоговую вероятность блэкаута и Топ-5 критических ветвей сети.
  - Сохраняет результаты в JSON по структуре:
    ```json
    {
      "benchmark_type": "Ray_Grid_Cluster",
      "timestamp": "ISO-8601",
      "cluster_info": {
        "num_nodes": 3,
        "total_cpus": 12,
        "node_ips": ["192.168.1.10", "192.168.1.15", "192.168.1.22"]
      },
      "config": { "trials": 100000, "chunk_size": 2500, "k_fault": 2 },
      "performance": {
        "execution_time_sec": 3.45,
        "throughput_trials_per_sec": 28985.5,
        "speedup_vs_single_cpu": 8.7,
        "cluster_efficiency_percent": 72.5
      },
      "metrics": {
        "blackout_probability": 0.0125,
        "top_critical_branches": [88, 133, 32, 39, 170]
      }
    }
    ```

### Шаг 5. Унифицированный CLI интерфейс (`run.py`)
Реализуй консольную точку входа со следующими режимами работы:
1. `python run.py local --trials 10000 --cpus 4` — локальный запуск (smoke-тест) без внешнего кластера (`ray.init()` в рамках одного компьютера).
2. `python run.py head --port 6379` — запуск управляющего узла (Head Node) с выводом команды подключения для воркеров (`ray start --head`).
3. `python run.py worker --head <HEAD_IP>:6379` — подключение машины в качестве рабочего узла (`ray start --address=...`).
4. `python run.py load --trials 100000 --head <HEAD_IP>:6379 --k 2` — запуск распределенной нагрузки на развернутом кластере с сохранением JSON-отчета.
5. `python run.py status` — вывод информации о текущих подключенных узлах кластера и их ресурсах.
6. `python run.py stop` — корректная остановка процессов Ray (`ray stop`).

## 5. Выделение сложных концепций (для будущего разбора)
В коде и в обучающем документе `stage2_explanation.md` явно пометь специальными блоками `[DEEP DIVE / СЛОЖНАЯ КОНЦЕПЦИЯ]` следующие 5 тем:
1. **Ray Object Store и Zero-Copy (`ray.put`):** почему нельзя передавать топологию сети как обычный аргумент в `@ray.remote`, как устроена разделяемая память Plasma и почему воркеры на одном узле читают данные без десериализации.
2. **Ray Task vs Ray Actor:** фундаментальная разница между stateless-задачами (`@ray.remote def ...`) и stateful-акторами (`@ray.remote class ...`); почему для Монте-Карло используются задачи, а для координации ресурсов — акторы.
3. **Проблема Stragglers и динамическая диспетчеризация:** почему жесткий барьер (`ray.get`) разрушает масштабируемость гетерогенного кластера, и как `ray.wait` реализует динамический пул потоков (Work-Stealing / Pull-based scheduling).
4. **Закон Густафсона-Барсиса (Gustafson-Barsis's Law):** почему закон Амдала пессимистичен для распределенных систем, и как масштабирование размера задачи ($N \to 10^7$) позволяет эффективно утилизировать сотни распределенных ядер.
5. **Отказоустойчивость задач (Fault Tolerance & Retries):** как Ray обрабатывает сбои и отключения физических воркеров (Heartbeats, Lineage Reconstruction, `max_retries`) и почему задачи симуляции обязаны быть детерминированными и идемпотентными.
